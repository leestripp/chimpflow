# OmniNet bug reports

Forwarded to the OmniNet dev team. Each entry: symptom, root cause
(file:line as of this checkout), suggested direction. ChimpFlow
(127.0.0.1:8090) proxies up to ~120 s of client audio to engine servers,
which is how these were hit.

---

## 1. `Config::maxRequestSize` does not control the actual upload ceiling

**Symptom:** A server sets `Config::maxRequestSize = 64MB`, yet any request
body over **10 MB** is still dropped mid-read (connection closed, no
response). The config knob appears to be ignored.

**Root cause:** `HttpConnection::readRequest()` enforces a hardcoded
`SAFETY_BODY_LIMIT = 10 * 1024 * 1024` (`src/http/HttpConnection.cpp`,
the `// Reading body` branch of the chunk loop). This check is independent
of `m_maxRequestSize`, so raising the configured limit has no effect past
10 MB. The related checks (`totalReceived > m_maxRequestSize * 2`,
`buffer.size() > m_maxRequestSize`) do follow the config — only the body
branch does not.

**Suggested direction:** derive the body cap from the configured value,
e.g. `bodyLimit = max(m_maxRequestSize, SAFETY_BODY_LIMIT)`, so
`SAFETY_BODY_LIMIT` remains a floor for servers that leave the default.
`Config::maxRequestSize` is then the single, documented knob for upload
size.

## 2. `Socket::send()` rejects single spans over 16 MB

**Symptom:** Any client/proxy that hands OmniNet a request body larger
than 16 MB in one buffer — e.g. a gateway forwarding a big multipart
upload via `HttpClient` — fails instantly with `SocketException("Invalid
send buffer")`, surfacing as `ClientError::SendFailed`.

**Root cause:** `Socket::send()` (`src/net/Socket.cpp`) throws when
`data.size() > RECV_BUFFER_MAX` (16 MB). But the caller `sendAll()` loops
over `data.subspan(totalSent)`, so a large span is legal by construction,
and `::send()` itself only writes what the kernel accepts. The receive
side already handles this correctly by clamping per call
(`actualSize = min(maxSize, RECV_BUFFER_MAX)`); the send side throws
instead.

**Suggested direction:** clamp on send like recv does:
`chunkSize = min(data.size(), RECV_BUFFER_MAX)` per call. `sendAll()`
then makes progress as intended.

## 3. `isValidApiKeyFormat()` splits key prefix at the *first* underscore

**Symptom:** API keys whose prefix contains more than one underscore are
all rejected with `invalid_format`, even when generated by OmniNet's own
`ApiKeyStore::create`.

**Root cause:** `TokenUtils.cpp::isValidApiKeyFormat()` uses
`find('_')` (first underscore) to separate prefix from secret, but
`ApiKeyStore::create` generates multi-underscore prefixes such as
`omn_sk_<hex>_<secret>`. Everything after the first underscore —
including the hex's own separators — lands in the "secret" part, which
then fails the alphanumeric check.

**Suggested direction:** split at `rfind('_')` (last underscore), or parse
from a fixed known prefix length instead of the first separator.
